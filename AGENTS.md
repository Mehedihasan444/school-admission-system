# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot, etc.) working in this repository. Read this file and `PRD.md` fully before changing anything. `PRD.md` is the source of truth for behavior; this file is the source of truth for *how to work*.

## 1. Project in one paragraph

School Admission System. A school opens first-come-first-served online admission. Applying creates a **hold** (a temporary seat reservation, default 600 s). Paying the fee **confirms** it; otherwise the hold **expires** and the seat is released automatically. Backend: C# / .NET 10 + PostgreSQL. Frontend: React 18+ + Vite + shadcn/ui (Tailwind). Everything runs with `docker compose up`.

## 4. Hard rules (do not violate)

### 4.1 API contract is frozen

- The 8 endpoints, paths, JSON field names, status codes in `PRD.md` section 5 must match exactly.
- You may **add** response fields. You may **never** remove or rename an existing one.
- Field names are `camelCase`. `status` values are exactly `HELD`, `CONFIRMED`, `EXPIRED`, `CANCELLED`.
- Timestamps are UTC ISO 8601 (`2026-11-01T04:10:00Z`).
- Seat full -> `409`. Cancel success -> `204` with no body. Create class -> `201`.

### 4.2 Concurrency and correctness

- `held + confirmed <= totalSeats` must hold under any concurrency and across multiple backend processes.
- Serialize through **PostgreSQL** (`SELECT ... FOR UPDATE` on the class row inside a transaction, plus atomic conditional `UPDATE`s). 
- **Never** use `lock`, `SemaphoreSlim`, `ConcurrentDictionary`, static counters, or any in-memory cache to enforce seat limits.
- Seat counts are **derived** from `holds` rows (`HELD AND expires_at > now` plus `CONFIRMED`). Do not add stored counters.
- A `HELD` row with `expires_at <= now` is expired in every read and write path, whether or not the background job has run. Correctness must never depend on the job.
- Confirm must be idempotent. Confirming twice must not increase `confirmedSeats` twice.
- A student has at most one active (`HELD`/`CONFIRMED`) hold per class. Keep the partial unique index.
- Use an injectable clock (`IClock` / `TimeProvider`) everywhere. No direct `DateTime.UtcNow` in business logic, so tests can control time.

### 4.3 Configuration

- DB connection string, `HOLD_DURATION_SECONDS` (default 600), CORS origins, and the frontend API base URL must be changeable through environment variables. No hardcoded values.
- Remember: `VITE_*` variables are baked in at **build time**. Use a Docker build arg or runtime-injected config so the URL stays env-driven.
- No secrets in the repo beyond local dev defaults in `docker-compose.yml`.

### 4.4 Data and Docker

- Data must survive `docker compose down` then `docker compose up`. Use a named volume for PostgreSQL.
- Migrations run automatically on backend startup (with retry until the DB is ready). The backend service waits for the DB healthcheck.
- A clean machine with only Docker installed must be able to run the project. Do not depend on locally installed SDKs.

### 4.5 UI

- Every action is possible from the UI. No requirement to use Postman or touch the DB.
- Expiry must flip the UI to `EXPIRED` and disable the pay button **without a page reload**.
- Class seat numbers auto-refresh every few seconds without reload.
- The student's running applications must reappear after refresh or reopening the browser (student ID in `localStorage`, applications loaded from `GET /me/holds`).
- Errors are shown as human-readable **Bangla** messages. No blank screens, no console-only errors. Keep an error boundary.

## 5. Conventions

### 5.1 Backend (C#)

- Target `net10.0`, nullable reference types enabled, file-scoped namespaces.
- ASP.NET Core with minimal APIs or controllers (stay consistent with whatever is already in the repo).
- EF Core + Npgsql for persistence. Use raw SQL (`ExecuteSqlInterpolated`, `FromSqlInterpolated`) for the `FOR UPDATE` lock and atomic `UPDATE`s. Always parameterized, never string concatenation.
- Async all the way, pass `CancellationToken`.
- Business logic lives in a service layer (for example `HoldService`), not in endpoint handlers.
- Errors: throw/return typed results and map them in one place to `{ "error": { "code", "message" } }` (see `PRD.md` 5.9).
- Validate input: `X-Student-Id` must be exactly 17 digits; `totalSeats` a positive integer; `name` non-empty.
- Names: `PascalCase` types/methods, `camelCase` locals, `_camelCase` private fields.

### 5.2 Frontend (React)

- React 18, TypeScript, function components and hooks.
- One small API client module; no `fetch` scattered across components.
- Prefer a data-fetching hook with polling (about 3 s) and cleanup on unmount.
- Countdown computed from `expiresAt`, ticking every second; reconcile with the server on each poll.
- Disable buttons while a request is in flight.
- Keep the UI simple. Correctness and clarity beat styling. Do not add heavy UI frameworks without a reason.

### 5.3 Commits (important: reviewers read the history)

- Commit **small and often**, as you work. Never end with one giant commit.
- Conventional-style messages: `feat: ...`, `fix: ...`, `test: ...`, `chore: ...`, `docs: ...`.
- One logical change per commit, and the project should build after each commit.
- Never commit build output (`bin/`, `obj/`, `node_modules/`, `dist/`) or `.env` files with real secrets. Keep `.gitignore` current.

### 5.4 Code quality and modularity (mandatory)

Professional, modular, readable code is a requirement, not a nice-to-have. Details in `TRD.md` 4.2 to 4.5.

**Structure**

- Organise by **feature**, then by layer inside the feature. Put each class, hook, and component in **its own file**; frontend feature components get **their own folder** (`Name.tsx`, `Name.test.tsx`, `index.ts`). shadcn/ui primitives stay as generated single files in `src/components/ui`.
- `Features/Classes` and `Features/Holds` must **not reference each other**. Shared concepts go to `Domain/` or `Shared/`.
- `Domain/` has **no** EF Core or ASP.NET references.
- Endpoints are thin: parse, call one handler/query service, map the result. No business rules and no DbContext in endpoints.
- Hold logic is split into use-case classes (`ApplyHoldHandler`, `ConfirmHoldHandler`, `CancelHoldHandler`, `HoldQueryService`), not one large service.
- Each backend feature exposes only `AddXModule()` and `MapXEndpoints()`. `Program.cs` just wires modules.
- Frontend: features import each other only via `index.ts`. `components/ui`, `lib`, and `shared` never import from `features`. No `fetch` in components; use feature hooks and api modules.
- **shadcn/ui + Tailwind** (details in `TRD.md` 4.3): add primitives with `npx shadcn@latest add <name>` and keep the CLI default paths from `components.json`; primitives stay generic (no business logic, no strings, no API calls); feature UI is composed from them; style only with Tailwind utilities and theme tokens via `cn()`, no CSS Modules or ad-hoc global CSS; icons from `lucide-react`; errors shown inline with `Alert`; Bangla-capable font in `index.css`.
- User-facing text only in `shared/i18n` (backend: `ErrorMessages.cs`). Status strings, error codes, header names, storage keys, and intervals are named constants.

**Style**

- One responsibility per file/function. Functions up to about 30 lines, backend files up to about 200 lines, React components up to about 150 lines. Split when larger.
- Descriptive names; booleans read like questions (`isExpired`). No dead code, no commented-out code, no unexplained `TODO`s. Comments explain *why*.
- Backend: nullable on, warnings as errors, constructor injection, records for DTOs, `async` with `CancellationToken`, EF config in `IEntityTypeConfiguration<T>` classes, one public type per file.
- Frontend: `strict` TypeScript, no `any`, typed props, hooks for stateful logic, effects clean up after themselves, handle loading/empty/error states, basic accessibility (`label`, `button`, `aria-live`).
- Keep pure logic (rules, formatting, validation) separate from I/O so it is unit testable.

**Tooling gates (run before every commit)**

```bash
dotnet format --verify-no-changes && dotnet build && dotnet test
cd frontend && npm run lint && npm run typecheck && npm run format:check && npm test
```

Do not disable analyzers, lint rules, or tests to make a check pass. Fix the cause.

## 6. Testing requirements

- Test files mirror the source structure (`tests/.../Features/<Feature>/...`, frontend tests next to the component).
- Backend: at least 3 automated tests, **one of them a concurrency test**. Target set: concurrency, duplicate student, expiry, confirm idempotency, ownership, contract shape.
- Concurrency test: create a class with N seats, fire many (for example 200) simultaneous apply requests from distinct student IDs, assert exactly N get `201`, the rest `409`, and `held + confirmed == N`.
- Use **real PostgreSQL** for tests (Testcontainers or the compose DB). Do not use the EF in-memory provider or SQLite for locking tests; they prove nothing about PostgreSQL behavior.
- For expiry tests use the fake clock or a very small `HOLD_DURATION_SECONDS`. Do not use long `Thread.Sleep`s.
- A bug fix comes with a test that fails before the fix.
- Frontend tests (bonus): Vitest + React Testing Library.

## 8. Working process for agents

1. Read `PRD.md`, then look at the existing code before writing new code.
2. State a short plan for non-trivial work. Follow the milestone order in `PRD.md` section 14.
3. Make the smallest change that solves the task. Do not refactor unrelated code.
4. Run build and tests. Fix failures at the cause, do not weaken or delete tests to get green.
5. Commit with a clear message.
6. Report what changed, what was run, and what remains.

### Ask the human first before

- Changing anything in the API contract (`PRD.md` section 5).
- Adding a new major dependency or changing the tech stack.
- Changing the database schema in a way that needs a data-destroying migration.
- Deleting files you did not create.
- Resolving a spec ambiguity that is not yet in `ASSUMPTIONS.md` and has real impact.

### Never

- Invent endpoints, fields, or behavior not in `PRD.md` and present them as part of the contract.
- Skip hold-expiry or ownership checks "for simplicity".
- Hardcode `localhost` URLs, credentials, or the hold duration.
- Leave TODOs or stubbed logic in code paths covered by the acceptance criteria.
- Claim a test passes without running it.

## 9. Definition of done

A task is done only when all apply:

- [ ] Behavior matches `PRD.md` (contract, rules, UI behavior).
- [ ] `dotnet build` and `dotnet test` pass; frontend builds (and tests pass if present).
- [ ] No new in-memory concurrency control; seat limits still enforced in PostgreSQL.
- [ ] Works from `docker compose up --build` on a clean state.
- [ ] Config is env-driven, no hardcoded values.
- [ ] `README.md`, `ASSUMPTIONS.md`, `AI_USAGE.md` updated where relevant.
- [ ] Changes committed in small, well-named commits.
- [ ] Code follows the modular layout and quality rules in section 5.4 (feature folders, one component/class per file, no cross-feature references, no business logic in endpoints/components).
- [ ] Lint, format check, type check, and analyzers pass with no suppressions added.
